Bypassing the WPS Slideshow FPS Limit on Linux

A record of improving WPS Office PPT playback frame rate on Arch Linux by scaling QElapsedTimer and accelerating time with libfaketime.

Published May 2, 2026Last updated May 2, 2026Category Linux

Because there is no hardware acceleration, WPS Office for Linux has a clear problem when playing PPT files: slideshow animations are often capped near 24 FPS, which looks poor when smooth transitions are used.

The community has proposed an approach: first make QElapsedTimer::elapsed() and QElapsedTimer::restart() return smaller time values. WPS still judges animation progress according to its original logic, but the time it sees passes more slowly. Then use libfaketime to speed the process time back up. When the two operations are combined, the goal is to make WPS trigger frames more frequently while keeping the animation speed as unchanged as possible.

Code repository

Problem Model

If WPS internally schedules slideshow animation at roughly 40 ms per frame, the actual frame rate is:

1000 ms / 40 ms = 25 FPS

If WPS can be made to think that only 20 ms has passed, it will not advance the animation state as quickly; but if the process time is accelerated by 2x at the same time, then 20 ms in the real world looks like 40 ms to the application. This may make the scheduler wake up more frequently while the animation timeline still advances at close to the original speed.

The default parameters are:

WPS_FAKE_SPEED=2.0
WPS_QELAPSED_SCALE=0.5

That is:

  • libfaketime speeds time up by 2x;
  • QElapsedTimer return values are multiplied by 0.5;
  • the theoretical target is close to 48 FPS while preserving the original animation speed.

If you want to try something close to 60 FPS, use:

WPS_FAKE_SPEED=2.5
WPS_QELAPSED_SCALE=0.4

Identifying and Exporting WPS Bundled Qt Timer Symbols

At first, it is easy to assume that intercepting the normal Qt5 symbols is enough:

QElapsedTimer::elapsed()
QElapsedTimer::restart()

But WPS on this machine does not directly use the system Qt. It ships its own Qt library:

/usr/lib/office6/libQt5CoreKso.so.5.12.12

After checking the symbols, WPS’s Qt classes are found under the kso_qt namespace:

kso_qt::QElapsedTimer::elapsed() const@@Qt_5
kso_qt::QElapsedTimer::restart()@@Qt_5
kso_qt::QElapsedTimer::nsecsElapsed() const@@Qt_5

So the preload library must export these symbols with the kso_qt namespace and the Qt_5 symbol version. Otherwise WPS will not call our implementation at all.

The corresponding mangled names are:

_ZNK6kso_qt13QElapsedTimer7elapsedEv
_ZN6kso_qt13QElapsedTimer7restartEv
_ZNK6kso_qt13QElapsedTimer12nsecsElapsedEv

Covering Direct Timer Calls Inside QtCore

LD_PRELOAD can intercept external symbol references during dynamic linking, but WPS’s bundled QtCore also contains many direct internal calls:

kso_qt::QUnifiedTimer -> kso_qt::QElapsedTimer::elapsed()

These calls happen inside the same shared library. They do not necessarily go through the PLT, so they may not be replaced by LD_PRELOAD.

This is important. PPT animation scheduling is likely located in QtCore’s QUnifiedTimer. If only calls from other WPS .so files to QElapsedTimer are intercepted, the hook may appear to work, but the path that actually affects animation scheduling is still not changed.

Therefore, the final implementation has two layers:

  1. Export same-name, same-version QElapsedTimer symbols to handle external dynamic symbol references.
  2. After process startup, apply an inline patch to WPS QtCore’s internal elapsed(), restart(), and nsecsElapsed() so direct calls inside the library also jump to our scaling logic.

The basic inline patch process is:

  • find the original function address in WPS QtCore;
  • verify the machine-code prefix at the start of the function to avoid patching incorrectly after a WPS update;
  • generate a trampoline that preserves the original function prefix and jumps back to the rest of the original function;
  • change the original function entry to jump to our hook function;
  • the hook function calls the trampoline to get the original time, then multiplies it by the scaling factor before returning.

This is more aggressive than plain LD_PRELOAD, but it is more direct for this scenario.

Launcher Script

The final launcher script does several things:

export WPS_QELAPSED_SCALE=0.5
export FAKETIME="+0 x2.0"
export LD_PRELOAD="/path/to/libwps_qelapsed_scale.so:/usr/lib/faketime/libfaketimeMT.so.1"
exec /usr/lib/office6/wpp "$@"

In actual use, start it like this:

bin/wpp-fps-unlock demo.pptx

You can also tune the parameters:

WPS_FAKE_SPEED=2.5 bin/wpp-fps-unlock demo.pptx

If inline patching fails after a WPS update, disable it first for troubleshooting:

WPS_QELAPSED_INLINE=0 bin/wpp-fps-unlock demo.pptx

Verification

There are two small probes to verify whether the implementation really works.

The first probe dlopen()s WPS QtCore at runtime and then calls QElapsedTimer:

make verify-runtime

The result shows that a normal 120 ms measurement is scaled down to 60 ms:

elapsed_default_ms=120
elapsed_direct_ms=120

elapsed_default_ms=60
elapsed_direct_ms=60

The second probe loads WPS QtCore as a startup dependency, simulating the case where QtCore already exists when the WPS process starts:

make verify-startup-patch

The result also shows that directly calling elapsed() at QtCore’s own address is affected by the inline patch:

startup_direct_ms=120
startup_direct_ms=60
